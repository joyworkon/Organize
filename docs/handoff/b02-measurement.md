## 1. 仪表修复（R12 两项缺口）

新模块 `apps/web/lib/perf/probe.ts`：**应用层直报**，不再包装 fetch（R12 的坑：
supabase-js 模块加载时捕获 `window.fetch` 引用，事后包装不生效）。

| 仪表 | 数据源 | 说明 |
|---|---|---|
| `savePosts` | `note-save-session.runSaveRound` 每次 RPC 后上报 | 成功/失败分开（`saveFailures`），含 RPC 名、耗时、内容字节数（近 500 条明细） |
| `draftSize` | `note-save-session.persistDraft` → `local-draft.writeLocalNoteDraft` | 写入字符长度（`body.length`，UTF-16 码元；CJK 场景 ≈ 字符数，比 UTF-8 字节数小）与序列化+存储耗时；`draftBytesLast/Max` 双口径 |
| 长任务 / INP 原料 | `PerformanceObserver`（longtask / event timing），首个客户端组件挂载时启用 | 覆盖全应用生命周期 |

**人工抽查方法**：打开任意笔记 → 打字 → 等「已保存」→ 浏览器控制台执行：

```js
__organizePerf.snapshot()
// => { savePosts, saveFailures, avgSaveMs, draftBytesLast, draftBytesMax,
//      longTaskCount, longTaskTotalMs, longTaskMaxMs, inpMaxMs, inpP75Ms,
//      serializationAvgMs, memory, lastSave, lastDraft, ... }
```

测量驱动与人工抽查读同一实例（`window.__organizePerf`），无第二套口径。
仪表代码 7 条单测（`lib/perf/probe.test.ts`），SSR/node 环境安全 no-op。

## 2. 测量方法

- **环境**：Apple M4 / 16 GB / 10 核，macOS 26.6.2（darwin arm64）；Playwright Chromium 1.62.1（生产构建 bundle）；本地真实 Supabase 后端（Docker）；协作关闭（不配 `NEXT_PUBLIC_COLLAB_WS_URL`，走乐观锁主链，与 R12 口径一致）。
- **驱动**：`apps/web/scripts/perf/measure.mts`（非 CI，本地实跑；原始数据 `/tmp/b02-perf/measure.json` 随 PR 留档于报告表）。
- **样本**：每轮 `service_role` 重新播种同起点；中文文本由固定种子 `SEED=0xb02f00d` 的 mulberry32 从 400 字乱序池拼接（驱动内可复现）；图片为 `/perf-img/N.png` 由路由就地 fulfill 的 1×1 PNG（消除网络/远图噪声）；图谱样本 60 笔记 × 5 标签 × 每篇 3 内链。
- **口径**：冷开 = 新浏览器 context 首次 `goto` 笔记页至编辑器可点击；打字 = 程序化聚焦后 500 字/批 insertText、间隔 10ms、共 2,000 字（列表1万/图谱为 0 字观察样本）；保存 = 防抖排空后读仪表；重开 = 同 context `reload` 至编辑器可点击；内存 = `performance.memory.usedJSHeapSize`（Chromium 专有）。
- **轮次**：每配置 3 轮；表中为中位数（最小–最大）。登录后预置 `organize:onboarded` 跳过首引导。

## 4. 瓶颈排序（按实测影响）

1. **编辑器大列表渲染（严重）**：1 万条 bulletList 笔记**冷开 71.6 秒**才可交互（重开 1.6s——SW 资源热后仍要重建 1 万个节点）。1 千条即 1.08s，呈超线性。这是唯一到「不可用」级别的证据点；属 TipTap/React 渲染层，修复方向是编辑器域（B04 块交互拆分/虚拟化另议），**不是**本地存储问题。
2. **大文档保存 RPC（中）**：5 万字平均保存 88–140ms（单轮离群 273/334ms），列表1k 154ms、列表10k 1.26s。全部发生在防抖后台，未阻塞输入（长任务 0）。
3. **图谱页首开（轻）**：60 笔记规模 886ms、内存 35.6MB（其余样本 19.6MB）。规模到千笔记级才需要关注。
4. **其余全部无瓶颈**：9 格字数×图片矩阵冷开 173–262ms、重开 192–233ms、打字零长任务——与 R12 主结论一致并扩展到图片/表格场景。

## 5. B06（本地存储优化）判断：维持「不实施」

- 草稿峰值仅 92.5KB（5 万字×30 图）；列表1k 267KB——离 localStorage 配额（~5MB）远；
- 序列化+存储单次 <1ms，打字期间零长任务；
- R12 与本轮两轮独立测量均无「同步 localStorage 写入为瓶颈」的证据。
按 B06 卡面「无瓶颈证据则取消并记证据」的约定，建议在账本将 B06 转**取消（证据充分）**，把实测瓶颈（大列表渲染）登记为编辑器域候选卡。
