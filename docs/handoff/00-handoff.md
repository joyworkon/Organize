## 3. 两条工作的衔接

推荐顺序：

1. 设计 agent 先在仓库外完成 D00–D01 独立设计预览，用户可以先看一版。
2. 工程 agent 在仓库执行 R00，然后逐卡执行 R01–R06 的可靠性修复。
3. 工程 agent 顺序完成 R07–R09 的职责拆分。
4. 选定设计方向后，设计 agent 在同步后的最新代码上执行 D02–D05 正式接入。
5. 最后安排 R10–R12 的数据能力和性能工作，以及 D06 次级页面统一。

只有“仓库外设计预览”与工程工作可并行。两个 agent 不得同时切换同一个 checkout 的分支、改 `globals.css`、主布局、笔记页或主编辑器。仓库约定一次只在一条特性分支上工作，遵守它；不要为了并行自行建立多条实现分支。

设计第一版无需等待保存层重构，但不得在原笔记页面复制一套可编辑器与保存逻辑。正式接入必须复用拆分后的业务入口。

## 4. 每张任务卡的执行协议

1. 读 AGENTS.md 和卡片引用的文件，报告当前基线、工作区状态、该卡复现结果。
2. 按仓库要求同步 master，再从最新 master 建 `fix/`、`chore/`、`feat/` 分支。执行前妥善保存其他人的改动；若用 stash，只保存明确路径并记录 stash id，恢复时也用该 id，禁止盲目 pop、reset 或 clean。
3. 同步失败时记录失败，禁止把旧 origin/master 当成最新。可继续只读分析或仓库外设计；不要基于未知旧基线启动实现。
4. 只做一张卡，不顺手全仓格式化、不升级依赖、不改无关文件。必要关联文件可增加，但解释原因。
5. 问题修复先有失败用例或可复现步骤，再最小修复，再验证。纯视觉改动无需大量结构快照测试，交互和数据行为需要测试。
6. 完成后提交 PR，遵守仓库 CI、squash 和分支清理规则。合并/发布按用户授予的权限执行；本计划本身不代表生产部署指令。
7. 未通过验收就停在当前卡，写清失败；不要通过删测试、跳过权限、吞异常或改预期来凑通过。

## 5. 验证与完成定义

通常每个工程 PR 执行：

```powershell
pnpm --filter @organize/web typecheck
pnpm --filter @organize/web test
pnpm --filter @organize/web exec next lint --dir lib --dir components --dir app --max-warnings 0
```

构建及浏览器测试使用项目现有配置。`pnpm --filter @organize/web e2e` 依赖 3100 的生产构建，mock 开关必须在 build 时注入，不能拿真实构建的服务器假称 mock。执行前读 `playwright.config.ts` 和 CI；不要覆盖用户 `.env.local`。数据库改动运行 `supabase test db`；缺 Docker/真实服务时明确标记未验证，不能把 mock 测试当成 RLS/多人协作证明。

`COLLAB_E2E=1` 才运行真实协作场景；修改保存/同步/权限后必须安排这些验证。对于生产构建、依赖审计等沿用 CI，不擅自删除门禁。

一张卡完成 = 范围实现 + 对应验收通过 + 必需 CI 通过 + 无未解释的新失败。视觉第一版完成 = 指定页面和状态有可操作预览与截图，不等于业务已上线。
