# Organize 功能、交互与跨端体验审查及修复计划

审查日期：2026-09-06。代码基线：`8e3208f`。当前工作分支：`docs/product-experience-audit-20260906`。

本文件是本轮检查结果和待执行计划，条目均未标记为已修复。范围包括笔记、待办、速记、整体 UI、macOS 刘海入口，以及手机和平板布局。

## 结论

产品的基本分工合理：速记用于捕捉，笔记用于整理，待办用于行动；速记转笔记、笔记关联任务也已经形成了连接。暖白底、炭灰字、陶土色强调的视觉方向适合长时间阅读和知识管理，建议保留。

当前主要问题是可靠性和跨端体验没有统一：中文输入可能误提交，速记没有草稿恢复，不同笔记创建入口的离线能力不同；部分错误会显示成空列表；手机和平板在操作入口、弹层尺寸、固定工具栏方面存在明确缺陷。暗色笔记正文和刘海自动收起应优先处理。

本次列出 **28 项修复或改进事项**：16 项 P1、11 项 P2，以及 1 项必须真机验证的 P1 候选风险。这里的数量包含设计改进和测试缺口，并非 28 个都已在生产环境复现的缺陷。

| 优先级 | 含义 |
| --- | --- |
| P1 | 影响输入、保存、数据可信度、可读性或核心操作可达性，先修 |
| P2 | 不阻断主要流程，但影响发现、效率、一致性或维护，随后修 |

## 功能与数据体验

### F01 · P1 · 中文输入法和快速重复提交没有统一防护

**证据：代码确认，中文真机输入仍需补测。** [速记输入处理](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/memos/page.tsx:240)只检查 Enter/Shift；编辑速记也一样。[任务快速添加](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/tasks/page.tsx:764)没有 composition 检查，也没有请求中的互斥锁，每次调用生成新 ID。[子任务输入](/Users/k/Documents/ZCode/Organize/apps/web/components/tasks/task-hierarchy.tsx:242)、任务标题编辑、刘海快捷输入也存在未统一的处理。刘海主速记框已经检查 `isComposing`，应保留并统一到其他入口。

**影响：** 确认中文候选字的 Enter 可能被当作提交；慢网络下连续 Enter 可以重复创建任务。异步返回后清空输入还可能覆盖继续输入的内容，见 F02。

**修复：** 统一 composition 生命周期和提交快捷键处理；按入口增加请求锁和稳定提交 ID。桌面速记保留现有快捷操作并支持 Cmd/Ctrl+Enter；手机 Enter 用于换行，保存按钮明确可见。

**验收：** 拼音选字不发送请求；连续 Enter/快速双击只产生一条；失败可重试；换行、中文标点、粘贴多行均正常。

### F02 · P1 · 速记草稿会丢失，保存中的继续输入也可能被清掉

**证据：站内导航复现 + 代码确认。** 速记的 `input`、`editContent` 仅在组件 state 中。[保存逻辑](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/memos/page.tsx:136)成功后直接 `setInput("")`，提交期间输入框仍可编辑。刘海速记同样保存后清空并延迟收起；任务快速创建直接清空 DOM input。

**影响：** 切换功能、刷新、关闭页面会丢掉未提交速记。提交 A 后继续写 B，A 的迟到响应可能把 B 清空。刘海窗口隐藏本身保留 React state，但重载或退出应用没有持久草稿保障。

**修复：** 按用户和入口保存本机草稿；成功时只清除被确认保存的那个版本。将“本机草稿”“待同步”“已保存”区分清楚。速记离线创建使用稳定 ID 和独立队列；服务端支持幂等后再启用自动重试，避免重复。应用重启恢复草稿，禁止静默覆盖其他窗口较新的草稿。

**验收：** 站内往返、刷新、离线、保存期间续写、应用重启都不丢字；旧请求完成不会清空新输入；退出账号后不会展示另一账号草稿。

### F03 · P1 · 数据读取失败会被呈现为空，部分编辑错误缺少反馈

**证据：代码确认。** [速记 fetchMemos](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/memos/page.tsx:93)忽略非 2xx 和网络异常，首屏失败之后显示“还没有速记”。[任务工作区查询](/Users/k/Documents/ZCode/Organize/apps/web/lib/tasks/workspace.ts:148)只解构 data，不处理各请求的 error；刘海查询也类似。速记编辑、删除没有捕获 fetch 抛出的网络异常，编辑也没有保存中状态。

**修复：** 区分 loading/error/empty/stale；主查询失败保留旧数据并提供重试，辅助数据失败单独说明。编辑失败保留输入且显示错误，增加提交状态。速记前端补齐服务端 5,000 字限制的计数和提示。

**验收：** 401、403、500、断网分别有合理反馈；已有内容不会被失败响应清成空；空列表只在请求成功且结果确实为空时出现；编辑失败无未处理 Promise rejection。

### F04 · P1 · 数据量增长后，列表与计数会出现静默截断

**证据：代码确认，未做大数据压测。** [速记 API](/Users/k/Documents/ZCode/Organize/apps/web/app/api/memos/route.ts:15)最多 500 条，页面没有翻页或继续加载，标签数量和“共 N 条”来自这一部分数据。笔记和任务主要列表没有分页，当前 [Supabase 本地配置](/Users/k/Documents/ZCode/Organize/supabase/config.toml:18)每请求上限为 1,000 行。生产上限需另行核实，不能把本地值直接当作生产值。

**修复：** 速记使用稳定排序的游标分页；标签统计和总数从服务器聚合。笔记/任务按视图分页或服务端筛选，并保证树结构、计数、搜索不依赖被截断的全量数组。大数据重构分域进行。

**验收：** 501 条速记及超过配置上限的笔记/任务仍可找到最早记录；加载更多不重复不遗漏；筛选、排序、计数一致；不通过一次无限量拉取所有正文来解决。

### F05 · P2 · 全局搜索结果没有定位到选中的任务或速记

**证据：代码确认。** [getItemPath](/Users/k/Documents/ZCode/Organize/apps/web/components/command-palette.tsx:137)把所有任务返回为 `/tasks`，所有速记返回为 `/memos`，丢失结果 ID。

**影响：** 用户已经找到了内容，点击后却回到列表，还要重新找；旧速记可能根本不在当前 500 条里。

**修复：** 任务跳到统一详情地址并带 task ID；速记提供 `?memo=` 定位、按 ID 补取、滚动及短暂高亮；工作台“最近速记”沿用同一地址合同。记录已删除时给出状态和返回入口。

**验收：** 从搜索、工作台、外部深链进入，都看到同一目标；未加载页中的记录也可定位；不会落回无上下文列表。

### F06 · P1 · Node 22 下网络状态首帧导致水合不一致

**证据：运行日志 + 本机运行时 + 代码确认。** 笔记、任务首屏均出现 hydration mismatch，差异是离线状态节点。[isOnline](/Users/k/Documents/ZCode/Organize/apps/web/lib/offline/network.ts:15)只判断 `typeof navigator`。本机 Node 22.22.2 中 `navigator` 是对象、`navigator.onLine` 为 undefined；SSR 因此不一定返回注释承诺的 true。hook 首帧直接读取该值，与浏览器首帧不同。

**修复：** 检查浏览器环境和布尔值类型，SSR 使用确定快照；hook 首帧与服务器一致，挂载后订阅真实网络状态。不要用 suppressHydrationWarning 掩盖。

**验收：** Node 22 构建/运行、在线及离线首屏没有 hydration warning；离线状态在挂载后正确显示；缺失 navigator/onLine 时工具函数仍返回布尔值。

## 笔记

### N01 · P1 · 暗色模式下正文低对比度，影响基本阅读

**证据：实测。** 默认新正文为 `rgb(55,65,81)`，实际背景为 `rgb(25,26,25)`，16px 普通文字对比度约 **1.693:1**。标题和侧栏正常，正文近乎隐没。[编辑器类名](/Users/k/Documents/ZCode/Organize/apps/web/components/editor/tiptap-editor.tsx:1164)使用 prose，没有把默认 Typography 正文色统一到暗色 token。

**修复：** 让正文、标题、列表标记、链接、代码、引用等 Typography 变量服从主题；处理 `sm:prose` 在不同断点的覆盖顺序。保留用户主动设置的文字和高亮颜色，另测这些组合。

**验收：** 手机/桌面默认正文两种主题均清晰；普通文字至少 4.5:1，大字至少 3:1，标准参照 [W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。包含列表、表格、代码、引用、历史预览和分享展示的代表性样本。

### N02 · P1 · 笔记“新建”入口的离线语义不同

**证据：代码确认。** 笔记列表有离线队列与错误提示；[createNewNote](/Users/k/Documents/ZCode/Organize/apps/web/lib/notes/create-note.ts:25)仍是 getUser + 直接 insert，失败返回 null；侧栏、标签条、刘海等复用它。全局 QuickAdd、命令面板另有直接 insert 分支。

**影响：** 同样是“新建笔记”，一个入口能离线创建，另一个可能没有任何结果；成功后的侧栏和标签刷新也不统一。

**修复：** 一个统一创建服务返回 created/queued/unauthenticated/failed；客户端生成 ID，沿用现有队列和保存协议；各 UI 只决定打开位置和文案。离线首次进入未缓存编辑路由的限制要明确处理。

**验收：** 列表、侧栏、标签条、QuickAdd、命令面板和刘海入口在断网/恢复网络时行为一致；同一条只创建一次；失败不静默。

### N03 · P2 · 只读笔记仍提供部分修改入口

**证据：代码确认，角色场景需真实后端回归。** 标题和正文根据角色只读，但 [NotePageVisuals/NotePageMenu 的调用](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/notes/[id]/page.tsx:1323)没有对应能力参数；封面、图标、父页面和页面设置等回调仍能改变本地展示。

**影响：** 用户可能先看到改动、随后才失败或刷新恢复，误以为系统保存不稳定。此项是前端能力表达问题，不等同于确认存在数据库越权。

**修复：** 将所有页面动作纳入角色能力映射；区分修改共享笔记、个人显示偏好、复制到自己的空间。无权操作隐藏或说明原因；明确拒绝的操作不先改变持久内容的本地状态。

**验收：** owner/editor/viewer 的工具栏、更多菜单、图标封面、父页面、历史操作分别匹配权限；服务端仍为最终授权依据。

### N04 · P2 · 笔记卡片逐项查询收藏，列表成本随条数增加

**证据：代码确认。** 每张 [NoteCard](/Users/k/Documents/ZCode/Organize/apps/web/components/notes/note-card.tsx:101)独立查询用户和 favorites；列表同时读取全部 content 以生成摘要。

**修复：** 列表层批量查询收藏状态；分页及摘要字段与 F04 配合，正文按需加载。先记录请求数和负载，再决定是否需要虚拟列表。

**验收：** 100 张卡片不会产生 100 次收藏查询；收藏切换、列表切换和搜索仍正确；记录优化前后的请求数量及响应体积。

## 待办

### T01 · P1 · 并发编辑失败时，整个任务数组回滚会撤销其他成功操作的显示

**证据：代码确认，需加入延迟/失败注入测试。** [updateTask](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/tasks/page.tsx:426)保存整个 `tasks` 快照，失败时 `setTasks(previous)`。编辑 A 尚未返回、B 已成功之后，A 失败仍可能恢复包含旧 B 的快照。同一任务多次更新也可能使用旧 sync_version 产生自冲突。

**修复：** 按任务 ID 和 mutation 管理乐观补丁及回滚；同一任务顺序写入，跨任务互不回滚。详情本地字段与失败结果同步，返回明确的保存结果。

**验收：** A 失败而 B 成功时 B 的显示和数据库保持一致；同一任务快速改标题、日期、优先级不自冲突；真正的远端冲突仍进入待处理，不静默覆盖。

### T02 · P2 · 普通任务完成后，侧栏计数停留在旧状态

**证据：实测 + 代码确认。** 创建测试任务后侧栏“全部 4 / 已完成 2”；完成该任务，主列表变为“待办 3 / 已完成 3”，侧栏仍是旧值。[完成处理](/Users/k/Documents/ZCode/Organize/apps/web/app/(main)/tasks/page.tsx:484)仅在生成下一次重复任务时发 `organize:tasks-changed`，而侧栏监听的是这个事件。

**修复：** 所有成功的任务变更通过统一状态源更新列表和计数，或稳定发出领域变更通知；避免为了通知导致整个主列表反复闪加载。

**验收：** 完成、撤销完成、删除、改清单、批量操作后，侧栏和主列表立即一致；离线乐观状态也保持一致。

### T03 · P2 · 日期显示和逾期判断的语义不一致

**证据：实测 + 代码确认。** [日期弹层默认触发器](/Users/k/Documents/ZCode/Organize/apps/web/components/tasks/task-date-popover.tsx:145)无条件红色，所以未来日期也是红的。列表的 [isOverdue](/Users/k/Documents/ZCode/Organize/apps/web/lib/tasks/workspace.ts:32)排除所有今天日期，且 taskDate 优先取开始时间；已完成任务也可能继续显示红日期。日期格式为 M/D/YY，与中文页面其他位置不统一。

**修复：** 明确定义“计划开始”和“截止”及全天任务语义；进行中跨天任务不能仅因开始日已过就判为逾期。红色只用于未完成且真正过期的截止；已完成中性展示。用统一的中文短日期和必要时的时间，避免只显示不明确的数字。

**验收：** 今天稍早已截止、未来日期、跨天任务、全天任务、已完成、取消、时区及夏令时样本在列表/详情/日历/刘海含义一致。
