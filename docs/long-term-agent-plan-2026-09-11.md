## 1. 先说结论

这个项目已经是功能较完整的个人知识与任务工具，不是只有界面的原型。最需要补的是“长期使用与发布后仍然可靠”，其次是降低以后改动成本，最后才是拓展功能。

建议按 3–6 个月的滚动路线管理，而不是承诺某一天实现全部功能。下面的波次是依赖顺序，不是工期保证。Agent 的 Token 余额不等于稳定的开发时间；剩余额度优先用于复现、实现、验证、审查和交接，不为了花完额度创造新需求。

本轮只调查并编写计划，没有修改业务代码、执行数据库迁移、连接生产数据或发布应用。

1. **SW 发布更新机制需要补强。** `public/sw.js` 仍用固定 `organize-v3`，网络失败统一回退 `/`；执行日志曾记录换版后旧页面/chunk 问题。本次确认代码形态，未现场重现发布事故。还需测试账号切换后的离线页面缓存隔离，不能未经复现直接宣称已泄露。

3. **协作身份刷新和存量连接撤权。** Hook 在建立连接时取得 token；现有合同是重连才复核权限。长期在线、退出账号、撤销公开链接需要专门验证和改进。

5. **性能报告不完整。** R12 仅有无图片样本；保存请求数和草稿大小仪表未有效采集，10/30 张图片与移动 Safari 未测。当前没有充分证据要求立即换 IndexedDB。
6. **重构仍有可控余量。** 笔记详情约 1,561 行、主编辑器约 2,264 行；R09 实际完成装配与上传拆分，块交互和协作适配仍留在后续。行数不是缺陷，只说明审查成本较高。
7. **生产与原生发布未被本次证实完成。** 桌面配置仍指向历史文档警示过的 `organize-web.vercel.app`；当前归属需重新验证。旧 BLOCKED 的 staging 迁移编号和登录态过时，不能直接照抄为今天的事实。

## 3. 以后改界面、增删整合功能，会不会越来越麻烦

会有不同程度的额外成本，但不需要因此推倒重建。已有数据、离线队列、权限和多个客户端让“改了还能兼容旧内容”成为开发的一部分。保存层抽离、统一收集入口和现有测试已经降低了这部分成本。

| 修改类型 | 相对成本 | 安全实施办法 |
|---|---|---|
| 配色、字体、密度、圆角 | 低 | 改统一 token，并覆盖 `use-theme-color.ts` 的 inline 变量 |
| 导航分组、菜单合并、列表布局 | 中 | 先列旧入口→新入口；保持 URL、快捷键、权限和状态可达 |
| 新增已有数据支持的筛选/视图 | 中 | 复用查询与服务，避免复制保存链 |
| 新增独立持久化功能 | 中高 | 同步做 schema、权限、mock、备份、垃圾箱及离线决定 |
| 改笔记/任务联动、协作身份或分享权限 | 高 | 先写状态与权限矩阵，测试后分阶段迁移 |
| 删除正文块类型、字段、任务关系 | 高 | 先停止新建/隐藏入口，保留旧内容读取、导出与恢复；最后才考虑清理 |
| 更换编辑器或整个数据模型 | 很高 | 只有明确收益和迁移验证后才立项，不作为日常改版手段 |

未来整合功能优先整合“入口和工作流”。例如将经验放在待办的复盘页，无须立刻把两张数据表合并；将图谱收进笔记入口，也无须删除 `/graph`。这样可以使产品更简单，同时保留旧数据和深链。

每次改版采用：一页目标说明 → 当前功能映射 → 独立交互预览 → 确定方向 → 一页一个 PR → 保存/权限/移动回归。视觉 PR 不夹带权限和数据模型变化。新版本至少有明确的上一版本内容兼容说明；无法兼容时给迁移与回退路径。

## 5. 可领取任务卡

规模 S：通常一张小 PR；M：一个完整小目标；L：先交设计，再拆若干串行 PR。不是 Token 或小时承诺。下列任务均为计划，未因本文存在而自动获得生产发布或破坏性操作授权。

### A01 建立唯一状态账本（S，立即可做）

- 输入：本文件及上述历史记录、实际源码、近期 PR。
- 交付：`docs/agent-workboard.md`，字段为 ID、状态、基线、证据、依赖、执行者、PR、未验证项；旧 ROADMAP/交接包顶部链接新入口，保留历史正文。
- 验收：R10a/R10b、R12 测量缺口、手机布局/原生发布不再混为完成；已完成项有实现证据。历史 BLOCKED 分为有效阻塞、已解除、合同说明。
- 边界：不借文档整理修改业务。新账本启用后，每张卡只更新该账本，不再让多个日志争夺“唯一真相”。

### A02 Service Worker 跨版本更新与离线边界（M，A01 后）

- 范围：`public/sw.js`、现有注册入口、构建版本注入和离线提示。
- 先复现两个构建之间升级、旧标签页、断网刷新、未缓存 chunk；验证 A 退出/B 登录的缓存边界。

### A04 同步块双浏览器可靠性验收（M，A03 后）

- 范围：073 协议、同步块组件、pending 存储；复用 R05 设计，不重新造同步协议。

### A05 协作会话刷新与撤权（L，A03 后）

- 先设计：token 刷新、账号退出/切换、viewer 降级、空间撤权、公开链接关闭/过期的状态图；定义并测试最长撤权生效窗口。

- 验收：token 过期前后继续编辑无丢字；旧账号连接关闭；撤权后存量连接无法继续收发未授权内容；本地未提交内容仍可导出；无重复播种/重复监听器。

## 6. Agent 如何接力

### 领取与完成

同一个 checkout 同一时间只有一个写代码的 Agent。其他 Agent 可以在仓库外只读审查、写设计或准备验收步骤；不能同时 git checkout、stash、改 lockfile、改迁移或启动共享后端。遵守仓库“一次一条特性分支”，不为了并行擅自创建多个实现分支。

每卡：确认依赖与独占权→保护现有改动→同步 master→建 feat/fix/docs/chore 分支→复现/基线→实现→验证→更新账本→PR→CI 通过后按已有授权合并→删除分支→同步。没有独占权时只读工作，不能 stash 其他 Agent 的改动。

状态只能用：候选、就绪、进行中、待验证、阻塞、完成、取消。代码已写但真机/真实后端未测，必须标待验证；因不值得实施而取消也是有效结果。

完成定义：范围满足；相应验证有命令/环境/结果；没有隐藏数据损失或权限退化；文档与 PR 可追踪；剩余缺口写清。不得靠 skip、删测试、放宽断言、空实现或假成功交付。

### 验证层次

业务改动沿用仓库门禁：web typecheck、Vitest、零警告 lint、build；UI/用户路径改动跑相关 E2E；数据库改动跑隔离本地 pgTAP，含越权负例；协作改动跑 collab-server build/test + 真实协作 E2E；Rust 改动跑相关 Rust 检查和设备验证。纯文档只做链接/内容检查，无需重跑业务全套。历史数量是参考，开工需建立当前基线。

新表/字段逐项检查：真实库、RLS/GRANT、mock、备份/恢复、垃圾箱、共享可见性、离线策略、旧数据兼容。不得直接 reset 当前用户库来获得干净测试，使用隔离环境。

### Token 使用和交接

- 余额较少：A01/C01 的一个小交付、独立审查一个 PR、补一个已复现缺陷的行为测试；不要开启半个大型迁移。
- 余额中等：A02/A04/B02 这类边界清楚的任务；先完成一个闭环再领下一张。
- 余额充足：A03/A05/B03 等高依赖卡，先设计和验证，再按子卡串行完成。
- 每完成一张卡保存工作，不等额度快耗尽才交接。新 Agent 先看最新 commit/工作树/账本，不能假定上一个的分支和进程仍在。
- 硬件或凭据阻塞时，交清单后转到就绪卡；同类失败反复出现时记录原因与证据，避免原地重复消耗。

## 7. 第一轮建议分配

1. 工程 Agent：A01→A02→A03→A04→A05（串行；每卡独立 PR）。
2. 审查 Agent：只读复核 SW、协作授权、备份；证据放仓库外，交给工程 Agent 收编，不和它切同一目录分支。
3. 设计 Agent：C01、C06 独立预览；不要再次执行已完成的 D00–D06 旧计划。
4. 验收 Agent：准备 C03/C04 真机步骤、补 B02 仪表方案；需写代码或占用后端时排队交接。

第二轮优先 B01/B02，再根据证据决定 B03/B06/B07。原生扩张放在 Web 和恢复链稳定后；E 类功能只挑最有价值的一两项，避免所有模块同时加深。
