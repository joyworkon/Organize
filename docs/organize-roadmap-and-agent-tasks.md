## 1. 产品方向

Organize 的核心不是堆出另一个全能知识库，而是打通一条稳定闭环：

`收集网页 -> 阅读与高亮 -> 写笔记/任务/经验 -> 在工作台回顾 -> 可恢复地沉淀`

短期优先级依次是：

1. 数据不丢、状态不乱、错误可恢复。
2. 高频编辑与回顾流程足够顺手。
3. 再扩展离线、桌面、移动端和 AI。

## 4. 对抗式分工结论

**结论：可分工，但只能按耦合和可验收性分，不能按代码行数分。**

最可能失败的三点：

1. 两个 Agent 同时修改 `notes/[id]/page.tsx`、`tiptap-editor.tsx` 或迁移，产生语义冲突。
   门禁：同一时间这些高冲突文件只归一个任务包，其他 Agent 禁止触碰。
2. 普通 Agent 把“按钮出现”当作“功能完成”。
   门禁：每包都要求失败路径、刷新后状态和真实浏览器验收，不接受仅截图或仅类型检查。
3. 委派成本超过实现成本。
   门禁：少于半天且需要大量上下文重建的任务留给当前主 Agent；普通 Agent 只接文件边界清楚、验收可机械判断的包。

## 6. 并行与审查规则

- 一次只允许一个 Agent 修改编辑器核心、笔记详情页或数据库迁移。
- 每个 Agent 使用独立 worktree 和 `codex/`、`feat/`、`fix/` 等特性分支。
- 接任务时复制完整任务包，不要只发一句“继续完善”。
- 审查必须同时读取任务包和 diff；只看 diff 会漏掉未实现的需求。
- 普通 Agent 的 PR 不自动合并。先过 CI，再由主 Agent 按验收项复测。
- 表格/列表/拖动等编辑器改动必须验证旧 TipTap JSON，可见 DOM 正常不等于持久化正确。
- CI 已知偶发问题：`supabase/setup-cli@v1` 下载失败会让 db-test 挂掉（verify 不受影响），
  重跑 failed job 即可，非代码问题。
